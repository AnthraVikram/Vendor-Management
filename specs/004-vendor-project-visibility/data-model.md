# Data Model: Vendor–Project Visibility, Project Tracking and Dashboard Views

One Prisma migration, `20261108120000_vendor_project_visibility`, makes every change below. It adds no table. It adds two columns to `projects`, two to `vendor_project_links`, and three values to the `HistoryAction` enum, and it swaps one unique index for a partial one. No existing row is changed or deleted by the migration (FR-038). Prisma generates the enum values, columns, foreign key, index drop and plain index. Only the partial unique index and the two check constraints are written by hand (tasks T003).

## Changed tables

### `projects` (Feature 001)

| Column | Type | Rule |
| --- | --- | --- |
| `start_date` | `DATE`, nullable | Entered by staff. Empty on every existing project (FR-014) |
| `expected_completion_date` | `DATE`, nullable | Entered by staff. Empty on every existing project (FR-014) |

- Check constraint `projects_dates_ck`: `start_date IS NULL OR expected_completion_date IS NULL OR expected_completion_date >= start_date` (FR-015a). The API refuses the same case first with a 400 naming both fields.
- Prisma: `startDate DateTime? @map("start_date") @db.Date`, `expectedCompletionDate DateTime? @map("expected_completion_date") @db.Date`.
- No actual completion date column (FR-014a). See *Derived values*.

### `vendor_project_links` (Feature 001), shown to staff as **assignments**

| Column | Type | Rule |
| --- | --- | --- |
| `removed_at` | `TIMESTAMP(3)`, nullable, the same type as every existing timestamp column | Set when the assignment is removed. Null means current (FR-013) |
| `removed_by` | `UUID`, nullable, FK `staff_users(id)` `ON DELETE RESTRICT ON UPDATE CASCADE` | The staff member who removed it |

- Check constraint `vendor_project_links_removed_ck`: `(removed_at IS NULL) = (removed_by IS NULL)`.
- Drop unique index `vendor_project_links_vendor_id_project_id_key`. Generated by Prisma from removing `@@unique`.
- Add index `vendor_project_links_vendor_id_project_id_idx ON (vendor_id, project_id)` for lookups that include past rows. Generated by Prisma from `@@index`.
- Add partial unique index `vendor_project_links_current_key ON vendor_project_links (vendor_id, project_id) WHERE removed_at IS NULL` (Feature 001 FR-026 for current assignments, FR-013b for past ones). Written by hand, because Prisma cannot express a partial index.
- Prisma: remove `@@unique([vendorId, projectId])`, add `@@index([vendorId, projectId])`, `removedAt DateTime? @map("removed_at")`, `removedById String? @map("removed_by") @db.Uuid`, and relation `removedBy StaffUser? @relation("LinkRemovedBy", fields: [removedById], references: [id], onDelete: Restrict)`. `onDelete: Restrict` matches Feature 003's optional references, and prevents Prisma's default `SetNull` from conflicting with `vendor_project_links_removed_ck`. `StaffUser` gains `linksRemoved VendorProjectLink[] @relation("LinkRemovedBy")`.
- The row is never deleted again. `api/tests/unit/append-only.test.ts` adds `vendorProjectLink` to the models that may never be deleted.

#### Lifecycle

```text
(none) --assign--> CURRENT --remove--> PAST (read-only, final)
```

- **assign**: allowed when the vendor and project are both not archived (Feature 001 FR-026) and the pair has no current assignment. Earlier past assignments of the same pair do not block it.
- **edit role, scope, note**: CURRENT only. A PAST assignment gives 409 `ASSIGNMENT_REMOVED`.
- **remove**: CURRENT only. It sets `removed_at`, `removed_by`, `updated_at` and `updated_by`, archives the pair's schedules (Feature 001 FR-028), and clears the responsible vendor on the project's items with a `LINK_REMOVED` change (Feature 002 FR-005), all in one transaction. A PAST assignment gives 409 `ALREADY_REMOVED`. It is allowed on archived vendors and projects, as today.
- There is no restore and no delete (FR-013).

### `history_entries` (Feature 003)

The `HistoryAction` enum gains three values: `ASSIGNED`, `ASSIGNMENT_EDITED` and `UNASSIGNED`. The table itself does not change.

## History events added by this feature

Each assignment event writes **two** entries in the same transaction: one with `vendor_id` and one with `project_id` (research.md §2).

| Event | Action | `changes` | `details` |
| --- | --- | --- | --- |
| Vendor assigned to project | `ASSIGNED` | `{}` | `assignment_id`, `vendor {id, name}`, `project {id, name}`, `role_on_project`, `scope_of_work`, `note` |
| Role, scope or note edited | `ASSIGNMENT_EDITED` | `diffFields` over `role_on_project`, `scope_of_work`, `note`. No entry when nothing changed | `assignment_id`, `vendor`, `project` |
| Assignment removed | `UNASSIGNED` | `{}` | `assignment_id`, `vendor`, `project`, `role_on_project`, `scope_of_work`, `note` |
| Project dates changed | `EDITED` on the project (existing event) | `start_date` and/or `expected_completion_date`, `from` and `to` as `YYYY-MM-DD` or null | unchanged |

`EDITED_FIELDS` in `projects/routes.ts` gains `start_date` and `expected_completion_date`.

## Derived values (stored nowhere)

Each value is worked out on every request from saved rows (NFR-002). "Today" is `todayInIndia()`. An item is **open** when its current status (latest progress update, `currentState`) is not `DONE` and it is not archived. "Overdue" is the Feature 002 `OVERDUE` flag from `flagsOf`.

### Assignment status (FR-010, FR-011), `lib/assignment-status.ts`

Input: the vendor's items on that project, meaning non-archived items with `responsible_kind = VENDOR` and `responsible_vendor_id` equal to the vendor. Each item is given as `{ status, overdue }`. The first rule that matches decides:

| # | Condition | Status |
| --- | --- | --- |
| 1 | no items | `NO_ACTIVITIES` |
| 2 | any item `overdue` | `DELAYED` |
| 3 | every item `DONE` | `COMPLETED` |
| 4 | any item `IN_PROGRESS` or `DONE` | `IN_PROGRESS` |
| 5 | otherwise, all `NOT_STARTED` | `NOT_STARTED` |

Labels shown to staff: No activities, Delayed, Completed, In progress, Not started. Past assignments have no status.

### Deadline group (FR-018), `lib/deadline-groups.ts`

For an open item on an active project:

| Deadline compared with today | Group |
| --- | --- |
| before today | `OVERDUE` |
| equal to today | `DUE_TODAY` |
| today + 1 to today + 7 | `COMING_SOON` |
| today + 8 to today + 30 | `UPCOMING` |
| after today + 30 | `null`, listed only under All |

Groups never overlap. The Feature 002 item flags (`OVERDUE`, `DUE_SOON`, `MISSING_UPDATE`) are unchanged.

### Project progress (FR-016, FR-016a), `lib/project-health.ts`

`{ done, total }` over the project's non-archived items, with milestones and activities counted alike. `total = 0` means "No activities yet" and no bar is shown.

### Project health (FR-017, FR-017a), `lib/project-health.ts`

The first rule that matches decides:

| # | Condition | Health |
| --- | --- | --- |
| 1 | `status = COMPLETED` | `COMPLETED` |
| 2 | `expected_completion_date` set and earlier than today | `DELAYED` |
| 3 | otherwise | `ONGOING` |

Overdue items never change health.

### Attention reasons (FR-023a), `lib/project-health.ts`

Only for active projects (not archived):

- `PAST_EXPECTED_COMPLETION` when health is `DELAYED`.
- `OVERDUE_ITEMS` with `count` when health is not `COMPLETED` and `overdue_count > 0`.

A project is listed when it has at least one reason. Order: `DELAYED` first, then `overdue_count` descending, then name.

### After project completion date (FR-015b), `lib/project-health.ts`

`isAfterCompletion(item, expectedCompletionDate)` is true when the date is set, the item is open, and `deadline > expectedCompletionDate`. `after_completion_count` counts these per project.

### Completed on (FR-014a)

When `status = COMPLETED`, this is the India date of the newest project `EDITED` history entry with `changes.status.to = "COMPLETED"`. Otherwise it is null (research.md §7).

### Vendor project count (FR-002)

The number of the vendor's current assignments whose project is not archived.

## Validation rules added

| Field | Rule | Response |
| --- | --- | --- |
| `start_date`, `expected_completion_date` | `YYYY-MM-DD` calendar date or null | 400 `fields.<name>`: "Enter a date as YYYY-MM-DD." |
| both dates | expected completion not before start, using stored values for the field not sent | 400 `fields.start_date` and `fields.expected_completion_date`: "The expected completion date cannot be before the start date." |
| link PATCH and DELETE | the assignment must be current | 409 `ASSIGNMENT_REMOVED` (edit) or `ALREADY_REMOVED` (remove) |
| link PATCH body | `.strict()`, unchanged: `assignment_status` or any unknown key is refused | 400 (FR-012: status cannot be set) |

## Seed additions (FR-032 to FR-035)

All records are find-or-create. Nothing is updated or deleted. Dates are relative to the India date the seed runs.

- **Staff**: the existing three accounts, unchanged.
- **Vendors**: 10 in total, the existing 2 plus 8 new, across 7 categories (Carpentry, Electrical, Plumbing, Tiling, Painting, False ceiling, Glass and aluminium). Phones are `98000000NN`, emails `@example.com`, and every name is fictional.
- **Projects**: 4 in total, the existing Lake House and Studio Fit-out plus two new. Statuses are Planned, Active, On hold and Completed. Two have start and expected completion dates, and one has an expected completion date in the past so it shows Delayed.
- **Assignments**: at least two vendors on more than one project and at least three on exactly one, with different roles and scopes. One past assignment is seeded with `removed_at` set.
- **Timeline items**: at least one each in Overdue, Due today, Coming soon and Upcoming. One In progress item has its last progress update 10 days back (Missing update), one is Done, and one has a deadline after its project's expected completion date. Together they give one assignment in each status: No activities, Not started, In progress, Delayed and Completed.
